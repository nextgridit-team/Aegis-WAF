# Optional sealed recovery cache

The default deployment keeps no local persistent application state. Without PostgreSQL, a new default replica remains unready. Existing replicas keep their last loaded configuration in memory.

For deployments that explicitly want restart recovery during a database outage, combine `compose.yaml` with the optional `compose.cache.yaml` overlay. It supplies a writable snapshot-cache volume and `SNAPSHOT_CACHE_FILE=/var/cache/aegis/snapshot.bin`. Each replica should have its own cache file/storage. This opt-in mode changes the default storage/readiness behavior; PostgreSQL remains authoritative.

The complete recoverable proxy configuration, certificate private keys, policy/rule snapshots and country database are sealed with AES-256-GCM using the existing external encryption key. Certificate keys are never written as plaintext files. Authenticated context binds the file to the key identifier, cache format and database connection string. Changing connection credentials therefore invalidates old cache files until a database-backed refresh writes a replacement. The cache contains no administrator sessions, bootstrap secret, external encryption key, ACME account keys or provider credentials.

A database-confirmed refresh writes a mode-0600 temporary file, flushes it and atomically replaces the old file. Unchanged snapshots refresh their cache timestamp every five minutes. Cache-write failure preserves the prior file and does not invalidate the active in-memory snapshot. Database failures do not refresh cache age. The file is bounded to 64 MiB; oversized configurations remain operational but cannot be cached.

Startup requires a valid authenticated file no older than `SNAPSHOT_CACHE_MAX_AGE` (default `24h`, positive and at most `168h`). Missing, stale, malformed, wrong-key, wrong-database or overly permissive files are ignored, leaving the replica unready until PostgreSQL works. Certificate/key matching, hostname coverage and configuration are validated on restoration; TLS validity checks and standalone rule expirations remain effective. Cached policy versions can be stale compared with changes made while this replica was offline, which is why the mode is explicit and age-bounded.

A successfully restored replica can serve its cached HTTP/TLS configuration and become ready before database initialization. Sign-in, administrator changes, HTTP-01 challenge lookup and coordinated ACME jobs still need PostgreSQL. When PostgreSQL returns, normal initialization/version refresh resumes and database configuration replaces or confirms the cached version. `/api/status` exposes cache enabled/available/restored flags when authentication is available.

The optional cache directory is the only additional persistent application mount. The image seeds it writable for non-root UIDs; the root filesystem remains read-only. Protect the host mount, maintain ownership for the platform-assigned UID and keep the mode-0600 file readable by that UID across replacements. If a platform changes UIDs, its storage permissions must be adjusted appropriately. No root init container, Docker socket, capability, extra worker or external service is required. The optional cache is not enabled on Nexus by this release.
