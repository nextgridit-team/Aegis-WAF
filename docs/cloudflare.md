# Cloudflare DNS-01 certificates

Cloudflare DNS-01 verifies domain ownership by creating a temporary public DNS TXT record. It does not require inbound port 80 and supports wildcard certificates. Cloudflare must manage the authoritative DNS zone. The site's web traffic does not need to pass through Cloudflare.

1. Create a Cloudflare API token with **Zone → Zone → Read** and **Zone → DNS → Edit**, scoped to the zones Aegis should manage. Use an API token, not the global API key or an Origin CA key. See [Cloudflare token creation](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) and [lego's provider permissions](https://go-acme.github.io/lego/dns/cloudflare/).
2. In Aegis, open **Certificate authorities → DNS providers → Connect Cloudflare**. Give the credential a name, paste the API token, and save. You can also connect it from the certificate request form; entered certificate details are preserved.
3. Open **Certificates → Request certificate**, select or register an ACME account and accept its CA terms, enter your hostnames, and choose **DNS-01 · Cloudflare**. Select the saved credential and request the certificate. Include both `example.com` and `*.example.com` if you need the apex and its subdomains.
4. Watch issuance status. Once valid, attach the certificate to a proxy host. Proxy host routing uses exact names; a wildcard certificate does not create wildcard routes automatically.

Tokens are encrypted with the external application key using AES-GCM and are never returned by read APIs. Editing a credential with an empty token keeps the existing token; entering a new token rotates it for subsequent issuance/renewal attempts. In-use credentials cannot be deleted. Tokens are not written to audit entries or normal service logs. Never place them in rule evidence or ordinary access logs.

Issuance and renewal reuse Aegis's database-backed jobs, account keys, advisory locking, backoff, and atomic certificate replacement. Cloudflare TXT creation uses the established lego Cloudflare provider. Aegis persists created record IDs so cleanup can recover across replicas or restarts; cleanup only removes those owned records, and preserves unrelated TXT records. Failed cleanup is retried, with stale records eligible for background cleanup after ten minutes. Certificate details show pending cleanup. An interruption between the external API creating a record and PostgreSQL persisting its ID cannot be made atomic; the adapter attempts immediate deletion on persistence failure.

The gateway needs outbound HTTPS to Cloudflare and the selected ACME CA, and DNS connectivity. TXT propagation checks use public recursive resolvers (1.1.1.1 and 8.8.8.8) with a two-minute bound to avoid accepting private split-DNS data. Local DNS policies or public CNAME delegation can affect discovery; investigate the public `_acme-challenge` records if validation times out. Permission and validation failures appear in job status and retry without replacing a working certificate. Start with the CA's staging environment before production.

No additional worker container, Docker socket, or local persistent application storage is needed for this integration. There is no Certbot service in this deployment; the application reuses its existing ACME client and lego's DNS-provider implementation.

Automated tests exercise encrypted credential APIs, a DNS-01 CA fixture with simulated Cloudflare records, wildcard issuance, replica coordination, cleanup and abandoned-record recovery, and renewal failure preservation. Browser tests cover credential management, challenge selection, and form preservation; Pebble still verifies real HTTP-01 issuance. Live Cloudflare/Let's Encrypt issuance requires the deployment owner's actual scoped token and domain and is not claimed by those fixtures.
